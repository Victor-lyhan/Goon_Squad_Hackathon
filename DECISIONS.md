# DECISIONS

One line per decision: date, decision, why. Humans seeded the first block from the spec review.

- 2026-11-14 Contracts live in `shared/` (types.ts, schemas.ts, api.ts), not `contracts/`, to match the spec's repo layout. Human-owned.
- 2026-11-14 All IDs deterministic per `shared/types.ts` conventions (plan-<shipmentId>, <planId>-L<i>, <employeeId>-eve/-morn). Needed for spec test 7 (same seed ⇒ identical assignments).
- 2026-11-14 Weight is kg in the form/request, grams in stored data (weightGrams = round(kg*1000)).
- 2026-11-14 Business has `district`; Node has optional `label`/`district` for friendly location names. UI never shows raw node IDs.
- 2026-11-14 Shipment has `clientRequestId` for idempotent POST and `createdSeq` for stable ordering.
- 2026-11-14 Shipment progress and job status are never stored; always derived from snapshotAt(run, clock.timeMin).
- 2026-11-14 Pickup at a trip's origin: service starts at max(departureMin, readyMin); waiting counts as added time. Delivery at a trip's destination: handling after arrival counts as added time.
- 2026-11-14 Stable event order at equal time: hub_drop before hub_pickup, then pickup, then delivered; ties broken by planId.
- 2026-11-14 Requests are validated with Zod on the server; responses are TypeScript types only (no runtime response validation) to save time.
- 2026-11-14 Static map data is served by GET /api/map (fetched once per runId) so the 1 s simulator poll stays small.
- 2026-11-14 jump_to_morning seeks to 5 minutes before the first Day 2 event (or 1860 if none).
- 2026-11-14 Dev ports: Vite 5173, API 3001. State file `data/state.json`, gitignored; missing file ⇒ load demo city.
- 2026-11-14 (M0) Styling is plain CSS in `client/src/styles/` (no Tailwind): no extra build config, and the UI kit in `client/src/ui/` keeps it consistent.
- 2026-11-14 (M0) `shared/` is imported by relative path (`../shared/types`, `../../shared/schemas`) from client, server and tests; no path alias, so Vite, Vitest, tsx and tsc all agree without extra config.
- 2026-11-14 (M0) Root `vite.config.ts` has `root: 'client'` and builds to `client/dist`; `vitest.config.ts` is separate and runs `tests/**/*.test.ts` in Node. `npm run build` builds the client only; the server is never compiled, `npm start` runs it with tsx and serves `client/dist` when it exists.
- 2026-11-14 (planner) Component tests are `tests/**/*.test.tsx`, rendered with `react-dom/server` renderToStaticMarkup (no jsdom/testing-library dependency). Issue #5 (p2-a) is authorized to add `jsx`/DOM lib to the root tsconfig and the `.tsx` include to vitest.config.ts. Until then, UI workers test pure `.ts` helpers (display models, geometry).
- 2026-11-14 (planner) UI test file prefixes, so workers never collide: p2-a `tests/ui/landing*|kit*|business*`, p2-b `tests/ui/employee*|commute*`, victor-2 `tests/ui/map*|sim*`.
- 2026-11-14 (planner) Shared display formatters (`formatMin` "Day 2, 8:30 AM", `formatCents`, `formatKg`, `formatDuration`) live in `client/src/ui/format.ts` (p2-a). Temporary local copies are allowed until it merges, then they get replaced.
- 2026-11-14 (planner) `routing.ts` is spatial only (shortest paths, baseline, insertion options sorted by extra driving, `buildTrips`). Handling, waiting, ready/deadline feasibility and the final insertion choice live in `matching.ts`. `buildTrips` is used by both matching and `PUT /commute`.
- 2026-11-14 (planner) `pricing.ts` exports `DEFAULT_SETTINGS` and per-plan price/reward/contribution; `metrics.ts` exports `computeMetrics({shipments, plans, unmatched, occurredEvents, settings})`. A leg's reward counts as earned when its final stop event has occurred.
- 2026-11-14 (planner) `store.ts` takes an `initial()` factory and holds one `Run`; file format `{schemaVersion:1, run}`; loading always forces `clock.playing=false`.
- 2026-11-14 (M0) Typecheck is three `tsc --noEmit` projects: `client/`, `server/`, and the root `tsconfig.json` (shared + tests + config files). New `.ts` files need an import or export (`isolatedModules`).
- 2026-11-14 (planner) Until `fixtures/demoScenario.json` holds a real Scenario, the server's initial run falls back to a `preset: 'fixture'` Scenario built from `fixtures/relayFixture.json` (no shipments), so UI work has real map data. `createApp(store)` is exported from `server/index.ts` so API tests can use a temp-file store.
- 2026-11-14 (planner) Clock logic is pure in `server/clock.ts` (`advanceClock`, `applyControl`). `play` sets `phase: 'locked'`; `reset_playback` keeps the phase. The timer and the control route only call these functions.
- 2026-11-14 (planner) Grid node IDs are `n-<row>-<col>` (x = col, y = row) from `gridGraph()` in generator.ts; the demo city is built on that grid.
- 2026-11-14 (planner, pass 3) Shipment progress maps straight from the last occurred event: none ⇒ `scheduled`, `pickup` ⇒ `picked_up`, `hub_drop` ⇒ `at_hub`, `hub_pickup` ⇒ `out_for_delivery`, `delivered` ⇒ `delivered`. Direct shipments therefore go Scheduled → Picked up → Delivered and skip "Out for delivery". Job status is `assigned` before the leg's first stop event, `in_progress` after it, and `completed` after its last stop event.
- 2026-11-14 (planner, pass 3) The clock ticker (`server/api/ticker.ts`) ticks every 250 ms, carries unconsumed milliseconds so `advanceClock`'s flooring never drifts, and calls `store.mutate` only while playing. Every playing tick bumps `run.version` and writes the state file; that's acceptable at this scale.
- 2026-11-14 (planner, pass 3) `generateScenario` lives in generator.ts (p1-b) and returns a Scenario. victor-1 writes `fixtures/demoScenario.json` from it (preset `demo`, fixed seed), so the demo city and the random city share one code path.
- 2026-11-14 (planner, pass 3) `PUT /commute` returns 409 while `phase === 'locked'` (spec §7: edits need a new planning cycle).
- 2026-11-14 (planner, pass 4) `assignShipments(shipments, ctx, { existing })` in matching.ts returns `computeMs: 0`, because domain code can't read clocks. Every `server/api/` caller times the call with `performance.now()` and overwrites `computeMs`. `existing` plans keep their trips reserved and are never re-planned. Result plans are ordered by shipment `createdSeq`.
- 2026-11-14 (planner, pass 4) Map markers exist only for employees with a planned leg, only between their trip's departure and `leg.finishMin`. Packages sit at the origin until pickup completes, follow the carrier, sit at the hub between drop and pickup completion, then sit at the destination.
- 2026-11-14 (planner, pass 4) Deep links: shipment tracking is `/business/<businessId>?shipment=<shipmentId>`; a job is `/employee/<employeeId>?job=<jobId>`. Portals open the tracking drawer / job detail from these query params.
- 2026-11-14 (planner, pass 4) `BusinessDashboard.totals.spendCents` = sum of `customerPriceCents` over the business's matched outgoing plans (committed spend, not just delivered).
- 2026-11-14 (planner, pass 5) The Demo city loads with its 24 packages already matched: `createInitialRun` runs `assignShipments` and `materializeAssignment` (`server/api/pipeline.ts`). That helper turns plans into jobs (one per leg), notifications and timeline events, and `POST /api/shipments` reuses it. A test guarantees free trips remain for a live demo request.
- 2026-11-14 (planner, pass 5) Notification IDs are deterministic: `ntf-<planId>-<businessId>` for `delivery_matched` (sender and recipient), `ntf-<jobId>` for `job_assigned`. Notifications are added only for plans that have none yet.
- 2026-11-14 (planner, pass 5) Direct vs relay comparison: `assignShipments` takes `opts.mode: 'with_relay' | 'direct_only'` (default with_relay), and `compareAssignments` in matching.ts runs both. Metrics per side are computed in `server/api/`.
- 2026-11-14 (planner, pass 6) `POST /api/shipments`, `PATCH /api/shipments/:id` and `POST /api/shipments/:id/match` return 409 while `phase === 'locked'`, like `PUT /commute`. `readyMin`/`deadlineMin` must fall inside `[simStartMin, simEndMin]`. PATCH only edits unmatched shipments. Unmatched shipments stay stored, and their reason comes from `run.assignments.unmatched`.
- 2026-11-14 (planner, pass 6) "Start new planning cycle" (`POST /api/planning/reset`) gives a new `runId` (`run-<n+1>`), rewinds the clock to `simStartMin` paused in `planning`, keeps businesses, employees, shipments and trips, and immediately re-runs full matching, so the portals are never empty after a reset. `POST /api/matches/recompute` does the same matching without the clock/runId change and is refused (409) while locked. Generate and import also bump `runId` so clients refetch `/api/map`.
- 2026-11-14 (planner, pass 6) New route handler files (`server/api/planning.ts`, `server/api/scenario.ts`) are built and tested unregistered, then wired into `server/index.ts` in one follow-up. That way two queued issues never both edit `server/index.ts`.
- 2026-11-14 (planner, pass 7) With must-haves 1–10 merged, the next priority is verifying the demo path with real data: UI tests render pages/components from `createInitialRun(loadDefaultScenario())` + `server/api/views.ts` output (never hand-written samples) and assert no `NaN`/`undefined`/raw node IDs. Tests under `tests/ui/` may import server code for this.
- 2026-11-14 (planner, pass 7) Business-portal maps (send-form mini-map, tracking route map) and the commute editor only draw routes returned by the API; the browser never runs pathfinding. Pending waypoints may be shown as markers before save.
- 2026-11-14 (planner, pass 8) Simulator deep link is `/simulator?package=<shipmentId>`: it opens with that package selected. Business cards, tracking and employee job detail link to it ("Watch in simulator").
- 2026-11-14 (planner, pass 8) victor-1 owns the root `README.md` (setup, scripts, state file, reset, demo steps). A test keeps its `npm run` commands in sync with package.json.
- 2026-11-14 (planner, pass 8) Demo step 7 (detour-limit tradeoff) is done with existing endpoints: new planning cycle → `PUT /commute` with a lower `maxExtraMin` → `POST /api/matches/recompute`. A commute save alone doesn't re-plan already-matched packages (existing plans stay reserved).
- 2026-11-14 (planner, pass 4) Portal read endpoints are built as pure functions in `server/api/views.ts` (`shipmentView`, `businessDashboard`, `employeeDashboard`, `jobResponse`) over `Run` + `snapshotAt`; route files only call them.
- 2026-11-14 (planner, pass 9) Every API error body is JSON `{ error: string, ... }`: 400 for validation, 404 for unknown business/employee/job/shipment IDs and unknown `/api/*` paths, 409 while locked. `client/src/api` errors expose `status` so portals can branch on 404 (#153).
- 2026-11-14 (planner, pass 9) Stale deep links (unknown IDs after Generate/Import) show a friendly "not in the current city" state with links to a valid identity and `/`. They never redirect silently and never use hardcoded IDs (#159, #164).
- 2026-11-14 (planner, pass 9) The "New" job highlight in the employee portal is in-memory only: the first load flags nothing, and a `runId` change resets the baseline (#163).
- 2026-11-14 (planner, pass 9) Verification issues name the files they may fix. A bug found outside those files is recorded as an `it.fails` test with a comment naming the file, and the planner queues the fix for its owner later. This keeps parallel issues from editing the same file.
- 2026-11-14 (planner, pass 10) A file touched by an open PR counts as taken: new issues name those files as "do not edit", even when the PR only needs a review. This keeps merges free of conflicts at the cost of some idle workers (p2-b gets one issue this pass).
- 2026-11-14 (planner, pass 10) An unreadable or unknown `data/state.json` loads the Demo city and keeps the bad file as a renamed copy. It is never overwritten silently (#184).
- 2026-11-14 (planner, pass 10) Generate city and Import replace the whole city, so the Setup drawer asks for confirmation first. Recompute and Start new planning cycle do not ask, because they keep the entities and packages (#189).
- 2026-11-14 (planner, pass 10) The landing page may show a live "Current city" summary (counts, matched/requested) read from existing API calls. Portal buttons on `/` always point to IDs that exist in the current city (#194).
- 2026-11-14 (planner, pass 11; written down in pass 12) No new `Metrics` field in `shared/` for #197. Per-trip added minutes and projected = actual are fixed inside `metrics.ts` (#214), and the unmatched-spend label is UI copy (#218).
- 2026-11-14 (planner, pass 12) When Recompute or Start new planning cycle changes a plan that keeps its ID (`plan-<shipmentId>`), its notifications are updated in place with the same ID so the text matches the current plan. Notifications for jobs that no longer exist are removed (#247).
- 2026-11-14 (planner, pass 12) The live demo request (sender, recipient, package, times, and the employee for steps 1 and 4) is written in README.md, and a test runs exactly those values on a fresh Demo city, so the demo script can't drift from the data (#243).
- 2026-11-14 (planner, pass 13) Ctrl-C/SIGTERM on the server stops the ticker, pauses the clock and writes the state file once more before exiting, so a restart resumes paused at the same minute. A busy port prints a one-line hint and exits with code 1 (#272).
- 2026-11-14 (planner, pass 13) At most 3 toasts are visible at once; extras are queued or folded into "+N more" (#277).
- 2026-11-14 (planner, pass 13) In the polish phase the planner doesn't queue filler to reach 4 `ready` issues. A worker gets fewer when its files are in open PRs or its area is already covered by spec tests.
- 2026-11-14 (planner, pass 14) Every portal poll passes an `AbortSignal` from #266 and aborts on unmount, identity switch and runId change. Aborts are silent and never count as connection failures. Network errors and timeouts keep the last data with a Reconnecting note, and HTTP errors show their message (#287, #288).
- 2026-11-14 (planner, pass 14) The health probe for the "Can't reach the Relay server" banner moves into `client/src/api` (#286), so no UI file calls `fetch` directly. It is not a `shared/` contract and returns a boolean.
- 2026-11-14 (planner, pass 16) The connection banner probes at most once at a time: a 3 s tick is skipped while a probe is still pending, and an aborted probe never counts as a failure (#298).
- 2026-11-14 (planner, pass 17) Domain tests that loop over generated cities give every test an explicit timeout with at least 3x headroom over the local time, and build each city once per file. CI runners are slower than local machines, and this is the second time a 5 s default turned main red (#213, #300).
- 2026-11-14 (planner, pass 12) Business notifications that arrive by polling show a toast once. They use the same in-memory "new since last poll" rule as employee jobs: the first load flags nothing, and a runId change resets it (#251).
- 2026-11-14 (planner, pass 18) If a CI-fix issue's cause turns out to be in another worker's files, the planner closes it and re-queues it for the owner, citing the CI log the worker quoted. The planner no longer guesses the cause from merge order: #300 blamed PR #297, but the log showed that the failing test came from PR #285 (#301).
- 2026-11-14 (planner, pass 19) The pass 17 timeout rule now applies to every test file, not just domain tests. Each worker sweeps its own test paths (#303–#308): an explicit timeout of at least 3x the local time and at least 10 s on any test over 1 s, data built once per file, and one test per seed. Perf and budget limits keep their numbers. A measurement above one third of its limit is reported in the PR, not loosened. One sweep per worker is not filler, because three CI timeouts have turned main red.
- 2026-11-14 (planner, pass 20) A test that takes more than 5 s locally is a finding, not just something to give a bigger timeout. Its owner finds out whether the time goes to the test or to a request the demo uses, then fixes the test or adds a latency budget for that request. First case: `notifications-cycles` (9.5–14.8 s) and the demo-step-7 commute PUT (#314).
